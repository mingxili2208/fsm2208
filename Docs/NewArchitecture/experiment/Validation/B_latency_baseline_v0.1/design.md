# 实验B：延迟与基线跟踪误差 - 设计说明

## 1. 引言与目标

### 1.1. 背景
尽管先前的实验（A.1, A.2）量化了系统的延迟和传感器的保真度，但它们并未直接衡量这些特性对车辆物理性能的实际影响。实验B旨在通过建立端到端系统延迟与物理车辆跟踪误差之间的定量关系，来弥合这一差距。

### 1.2. 主要目标
本实验的目标是建立一个**“误差基线” (Error Baseline)**：即完全由系统延迟所导致的、最小且不可避免的跟踪误差。这是通过验证以下物理模型来实现的：

**`纵向跟踪误差 ≈ 车辆行驶速度 × 系统总延迟`**

这个基线将作为一个关键的诊断工具，用于在未来更复杂的测试场景中，区分由平台限制引起的误差和由算法缺陷引起的误差。

## 2. 方法论与设计

本实验采用“并行数据采集、统一分析”的策略，以确保结果的可靠性。

1.  **延迟特性分析**：一个专用的记录器 (`latency_impact_logger.py`) 捕获“感知-规划-执行”流水线完整的端到端时间链。
2.  **物理误差测量**：第二个记录器 (`tracking_error_analyzer.py`) 在一个高度受控的、恒速直线行驶的测试中，测量车辆的物理跟踪误差。
3.  **对比分析**：最后的分析脚本 (`analyze_experiment_b.py`) 对比测量的物理误差与由延迟预测的理论误差，以验证模型的有效性。

### 2.1. 时间链定义
本实验测量四个关键的时间戳：
*   **T_actual**: 作为感知周期起点的地面真值数据的时间戳。
*   **T_percept**: 感知/定位模块输出结果的时间戳。
*   **T_plan**: 规划模块输出轨迹的时间戳。
*   **T_actuate**: 车辆控制节点开始处理规划指令以生成驱动命令的时间戳。

### 2.2. 关键延迟指标
*   **信息年龄 (Information Age)**: `T_percept - T_actual`
*   **规划器延迟 (Planner Latency)**: `T_plan - T_percept`
*   **决策到执行延迟 (Decision-to-Actuation Latency)**: `T_actuate - T_plan`
*   **端到端总延迟 (Total End-to-End Latency)**: `T_actuate - T_actual`

### 2.3. 受控测试场景
*   **路径**: 一条预定义的、已知长度的直线（例如200米）。
*   **速度**: 一个恒定的低速（例如0.5米/秒），以最小化动态效应。
*   **测量**: 分析的核心是**纵向跟踪误差**，其计算方式为车辆沿路径的实际行进距离 (`s_actual`) 与其理论目标行进距离 (`s_target = v * t`) 之间的差值。

## 3. 系统组件与逻辑

### 3.1. `latency_impact_logger.py`
*   **角色**: 全链路主计时员。
*   **逻辑**:
    *   订阅地面真值、感知、规划和执行时序的主题。
    *   使用 `deque` 缓冲区存储数据。
    *   采用由最终 `T_actuate` 消息触发的“反向链式关联”机制，高效地构建完整的时间链。
    *   将经过验证的完整时间链和计算出的延迟数据记录到 `exp_b_latency_data.csv`。

### 3.2. `tracking_error_analyzer.py`
*   **角色**: 物理误差测量的路测检察员。
*   **逻辑**:
    *   从配置中定义一条参考 `LineString` 路径。
    *   自动检测车辆是否位于路径起点附近，以启动测试。
    *   持续计算车辆相对于路径的Frenet坐标 (`s`, `d`)。
    *   计算纵向误差: `s_actual - (目标速度 * 经过时间)`。
    *   将所有跟踪数据记录到 `exp_b_tracking_error.csv`。

### 3.3. `carla_handler_patch.py`
*   **角色**: 为CARLA控制节点提供计时工具。
*   **逻辑**:
    *   拦截传入的规划轨迹。
    *   记录 `T_plan` (来自消息头) 和 `T_actuate` (当前时间)。
    *   在一个专用主题上发布 `(T_plan, T_actuate)` 时间对，供延迟记录器使用。

### 3.4. `analyze_experiment_b.py`
*   **角色**: 将所有数据整合成最终分析报告。
*   **逻辑**:
    1.  加载并清洗延迟和误差两个CSV文件。
    2.  **延迟分析**: 对所有延迟分量进行统计分解。
    3.  **误差基线分析**:
        a. 从延迟数据中计算平均总延迟。
        b. 计算理论误差 (`v * Δt`)。
        c. 从跟踪数据中计算实际平均误差。
        d. 计算**一致性比率 (Agreement Ratio)**: `实际平均误差 / 理论误差`。
    4.  **产出物生成**: 创建全面的图表、一个JSON格式的摘要文件和最终的Markdown报告。

## 4. 工作流程与执行

1.  **配置**: 审查并调整 `config.yaml` 中的主题、路径和阈值。
2.  **植入**: 将 `carla_handler_patch.py` 提供的补丁应用到系统的CARLA控制节点。
3.  **执行**: 启动完整的FSM Sandbox系统。运行 `start_experiment_b.sh` 脚本，该脚本会启动两个记录器节点。
4.  **测试流程**:
    a. 首先，正常驾驶车辆3-5分钟，以收集通用的延迟数据。
    b. 然后，将车辆定位到预定义测试路径的起点。
    c. 以配置中的恒定速度沿路径行驶。`tracking_error_analyzer` 将自动管理此测试阶段。
5.  **终止**: 使用 `Ctrl+C` 停止 `start_experiment_b.sh` 脚本。
6.  **分析**: 运行 `analyze_experiment_b.py`，并提供生成的两个CSV文件的路径。

## 5. 交付物与预期成果

### 5.1. 原始数据
*   `exp_b_latency_data_YYYYMMDD_HHMMSS.csv`
*   `exp_b_tracking_error_YYYYMMDD_HHMMSS.csv`

### 5.2. 分析产物
*   `latency_analysis_...png`: 延迟特性分析的可视化图表。
*   `error_analysis_...png`: 对比理论误差与实际跟踪误差的可视化图表。
*   `experiment_b_results_...json`: 包含所有数值结果、便于机器读取的JSON文件。
*   `experiment_b_report_...md`: 一份全面的、人类可读的报告，总结了实验的发现，包括最终的“一致性比率”和对平台性能的定性评估。

### 5.3. 预期成果
最主要的成果是**一致性比率 (Agreement Ratio)**。一个接近1.0的值（例如在 `0.8` 到 `1.2` 的范围内）将为以下结论提供强有力的证据：FSM Sandbox平台是物理自洽的，并且在简单的稳态条件下，其延迟是跟踪误差的主要来源。这成功地为未来更复杂的分析建立了一个可靠的“误差基线”。
